# 해외선물 실시간 대시보드 개발 계획

기준선 검토: 2026-11-06 소스와 `Res` 파일. 2026-11-07에는 그 뒤의 구현 변경과 주식·해외선물 TR이 한도를 공유한다는 사용자 설명을 반영했다. 아래 3절은 11-06 변경 전 기준선이고, 11절은 현재 구현 진행 상태다. Visual Studio MSBuild는 통과했으나 WPF 실화면·Xing 연결 응답·기존 DB 업그레이드는 아직 확인하지 않았다.

## 1. 목표

현재 해외선물 대시보드를 카드 목록 중심 화면에서 선택 계약의 일봉·10분봉·1분봉 차트와 OVC 실시간 체결 정보를 함께 보는 대시보드로 바꾼다. 사용자가 왼쪽 관심계약 목록에서 계약을 선택하면 해당 계약의 저장된 차트 데이터가 즉시 표시되고, XingAPI 응답으로 저장 데이터를 최신화한다.

계약 목록과 사용자 관심계약은 기존 기능을 그대로 사용한다. 전체 거래소 종목 마스터는 조회 결과를 메모리에 두고, 사용자가 선택한 관심계약만 기존처럼 데이터베이스에 보관한다.

## 2. 요청된 화면

아래 배치는 첨부된 oversea_chart_layout1.png의 구성을 따른다.

이미지의 하단은 ‘보조지표’, 분봉 영역은 ‘오버레이 지표추가’로 표기되어 있다. 이 문서는 그 배치를 참고하되 하단을 OVC 정보 패널로 사용하는 계획이다. 보조지표/오버레이 계산·표시는 아래 개발 범위에 포함하지 않으며, 이미지의 모든 기능을 구현하는 것으로 해석하지 않는다.

## 4. XingAPI 데이터 흐름

### 주식·해외선물 전체 공통 TR 호출 제한

사용자 설명에 따라 **주식과 해외선물 TR을 한데 합산해 초당 1건, 10분당 200건**을 적용한다. `o31XX` 코드만의 제한으로 분리하지 않는다. 현재 서비스의 o3101·o3103·o3104·o3105·o3106·o3107·o3108, 주식 시세/차트/종목 TR, 계좌·주문 TR과 이후 추가하는 일반 TR 요청은 모두 같은 제한기를 통과해야 한다.

- 앱 전체에서 공유하는 싱글턴 요청 스케줄러에 전송 대기열, 마지막 전송 시각과 최근 전송 이력을 둔다. 화면·계약·TR 코드·Query 인스턴스를 바꿔도 한도가 초기화되거나 늘어나지 않는다.
- 서로 다른 코드 사이에도 최소 1초의 전송 간격을 두고, 최근 600초에 합계 200건을 전송했다면 다음 허용 시각까지 대기한다. 최근 600초 이력을 사용하는 방식은 기간 경계에서 초과하지 않기 위한 보수적인 구현안이다.
- 관심계약 관리의 전체 마스터 조회(o3101), 상세 화면의 차트(o3108), 대시보드 분봉/일별 조회, 주식의 t1101/t8407/t8410/t8430, 계좌/주문 TR, 수동 새로고침, 연속조회 각 페이지와 재시도를 모두 같은 예산에 포함한다. 실시간 구독 데이터는 요청형 TR과 구분한다.
- 조회 응답의 행 수가 아니라 전송 호출 수를 센다. 예를 들어 분봉 2000행을 한 번 요청하면 1건이고, 다음 페이지를 요청하면 추가 1건이다. o3107의 여러 종목 일괄 조회도 한 번의 호출로 집계한다.
- 전송 허용 판정과 이력 기록은 하나의 경계에서 처리해 동시 호출이 한도를 우회하지 않게 한다. 아직 전송하지 않고 취소한 작업은 세지 않으며, 실제 호출을 시도한 작업은 보수적으로 집계하고 실패했다고 즉시 예산을 돌려주지 않는다.
- 주식 차트 전용 간격 큐와 o31XX의 직접 전송 경로를 앱 공통 스케줄러로 통합한다. 일반 조회·계좌·주문 요청 메서드가 직접 `Request()`를 호출해 공통 제한을 우회하는 경로를 남기지 않는다. OVC/OVH 및 주식 실시간 수신 이벤트는 요청형 TR과 구분한다.
- 호출 한도와 같은 TR의 미완료 요청 1개 제한은 별개다. 공통 스케줄러가 전송 간격/총량을 관리하고 TR별 요청 컨텍스트가 응답 전 입력 덮어쓰기를 막는다.
- 한도 대기는 오류나 응답 시간 초과와 구분해 ‘호출 한도 대기’ 상태로 표시한다. 응답 타임아웃은 실제 전송 후부터 계산하고, 대기 중 선택이 바뀐 미전송 작업은 취소/병합한다.
- `GetTRCountPerSec`, `GetTRCountBaseSec`, `GetTRCountLimit`, `GetTRCountRequest` 값은 전송 전 진단 로그에 기록한다. TR별 초/기준초 제한과 API가 보고한 요청/한도 제한이 전역 공통 한도보다 엄격하면 추가 대기한다. TR별 제한을 적용해도 전역 초당 1건·10분 합계 200건은 그대로 유지하며, 서버 오류 응답은 요청 실패/Query 격리로 처리한다.

### o3103: 분봉 차트

리소스 Res/o3103.res의 입력은 종목코드 shcode, N분 주기 ncnt, 조회 건수 readcnt, 연속 키 cts_date·cts_time이다. 요청 시 ncnt=1과 ncnt=10을 각각 사용한다.

응답 행은 날짜·현지시간·시가·고가·저가·종가·거래량으로 구성한다. o3103OutBlock에는 조회 건수, 시차, 다음 페이지용 연속 날짜·시간이 있다.

- 1분봉과 10분봉 요청은 한 번에 하나씩 보내고 해당 응답이 확인된 다음 요청을 보낸다.
- 현재 응답의 `Symbol`은 `o3103OutBlock.shcode`, 주기는 `o3103InBlock.ncnt`에서 읽는다. 입력 블록을 응답 전에 바꾸지 않고, 별도 요청 컨텍스트의 종목/주기와 응답 종목을 대조한다.
- 연속 응답은 IsNext와 연속 날짜·시간을 이용해 같은 종목·주기의 다음 페이지로 요청한다.
- 페이지마다 차트 저장소에 upsert하고 조회 완료 후 DB에서 정렬해 차트를 다시 만든다.
- 빈 페이지, `IsNext=false`, 연속 키 누락/반복, 설정한 시작일 도달, 최대 페이지/봉 수 도달 시 종료한다. 부분 수집과 정상 완료를 구분하고, 종목/주기마다 연속 키를 따로 보관한다.
- 현재 메서드는 주기/건수 각각 1~9999를 허용하고 기본 건수는 2000이지만 이는 로컬 입력 검증이다. 이번 화면의 주기는 1·10으로 제한하며 서버의 실제 허용 건수·조회 범위는 별도 확인한다.
- `TimeDifference`는 현재 이벤트로 전달될 뿐 변환/저장에 쓰이지 않는다. 원본 날짜·현지시간을 보존하고, 시차의 단위·부호 및 거래일/서머타임 규칙을 확인한 뒤 표시·변환 규칙을 정한다.
- o3103의 1분/10분 요청과 연속조회 각 페이지도 위 앱 공통 스케줄러를 통과한다. 자산/화면마다 별도 전송 간격을 두지 않는다.

### o3104: 일별 체결과 일봉 투영

리소스 Res/o3104.res 입력은 조회구분 gubun, 종목코드 shcode, 조회일자 date다. 출력 행에는 체결일, 현재가 price, 전일 대비 부호/값/등락률, 시가·고가·저가, 체결구분, 누적 거래량이 있다.

#### 첨부 설명으로 확인한 사항

![o3104 TR 속성 및 조회구분 설명](o3104_tr_properties.png)

| 항목 | 첨부 화면의 설명 | 계획에 적용할 내용 |
|---|---|---|
| TR 속성 | Header `A`, Attribute `O`, Block Mode `O`, TR 크기 `118` | 조회 포맷/블록 속성 참고값으로 기록. 크기는 API 조회 호출 횟수나 결과 행 수로 해석하지 않음 |
| 입력 블록 | `o3104InBlock`, 크기 `17`, 기본 입력, 비반복 | 입력 필드 `gubun`, `shcode`, `date`를 단일 요청 조건으로 설정 |
| 조회구분 `gubun` | string 1자리. `0`: 일별, `1`: 주별, `2`: 월별 | 대시보드 일봉 요청은 `RequestDailyTradeData(symbol, "0", queryDate)` 사용. 서비스 입력 검증은 `0/1/2`로 제한 |
| 종목 `shcode` / 조회일 `date` | 각각 string 8자리, 단축코드 / 조회일자 | 기존 종목코드 검증과 `yyyyMMdd` 전송을 유지. 조회일의 포함 범위/시장 날짜 기준은 실응답으로 확인 |
| 초당 전송 수 | 1초당 1건 | 사용자 설명에 따라 주식과 해외선물의 모든 일반 TR 전송 사이 최소 1초 간격 적용. 같은 TR의 미완료 요청 제한도 유지 |
| 기간별 제한 | 10분당 200건 | 사용자 설명에 따라 주식과 해외선물의 모든 일반 TR 전송 이력을 합산. 최근 600초에 합계 200건 도달 시 대기 |
| 출력 블록 | `o3104OutBlock1`, 크기 `101`, OCCURS | 여러 행을 읽는 기존 로직 유지. 반복 블록이라는 사실만으로 날짜별 유일성이나 연속조회 가능성을 가정하지 않음 |
| 가격/수량 | `price`: 현재가(double 15.9), `open/high/low`: 시가/고가/저가, `volume`: 누적거래량(long 10자리) | 원본 Price와 Volume 의미를 보존. Close 매핑은 아래 확인 후 확정하고 거래량은 기존 long 모델 사용 |

첨부 화면의 수치를 o3104만의 독립 한도로 해석하지 않는다. 주식 TR과 해외선물 o31XX가 초당/10분 예산을 공유한다. 예를 들어 같은 10분 집계 범위에 주식 t8410을 100회, 해외선물 o3108을 100회 전송했다면 다음 o3104도 한도가 열릴 때까지 대기해야 한다. 초당 제한만 지키며 계속 전송해도 10분 한도를 초과할 수 있으므로 두 제한을 함께 검사한다.

o3104 서비스를 호출하는 경우 대시보드 일별 요청의 `gubun`은 `"0"`으로 지정한다. 다만 현재는 조회 범위와 `price`의 일봉 종가 의미가 확인되지 않아 대시보드에서 o3104를 요청하지 않는다. 주별/월별 값은 서비스 검증과 요청 컨텍스트에 반영하되, 주·월봉 화면 추가는 이번 범위에 포함하지 않는다. `_dailyTrades` 캐시는 이미 `(Symbol, QueryType)`으로 구분하며, 향후 `"1"`/`"2"` 호출 때도 주·월 데이터를 `OFutureDailyBars`에 일봉으로 저장하지 않는다.

#### 일봉 투영 전 남은 확인

**현재 대시보드의 일봉 원천은 o3108이다.** 조회구분 코드의 의미는 첨부 설명으로 확인했지만, 화면의 `price`는 여전히 ‘현재가’이고 명시적인 `close` 필드는 없다. 따라서 일별 조회가 가능하다는 사실과 각 행을 확정 일봉으로 저장하는 규칙을 구분한다. o3104 사용을 계획에 유지하되 아래 확인을 1단계의 선행 조건으로 둔다. 확인이 안 되면 일봉 원천 결정은 미완료로 남기고, 기존 o3108 유지 여부를 별도 결정한다.

- 기존 RequestDailyTradeData(symbol, gubun, date) 및 OFutureDailyTradeData를 활용한다.
- 조회구분은 첨부 설명에 따라 일별 `"0"`로 지정한다. 조회일자의 포함 여부와 기준 시장 날짜, 반환되는 날짜 범위/순서 및 건수는 API 정의와 실제 응답으로 확인한다. 조회일만으로 조회 시작일/종료일을 임의 추정하지 않는다.
- 화면의 일봉 종가는 API price를 그대로 Close로 사용할 수 있는지 응답 의미를 확인한다. price가 특정 체결가인 경우에는 날짜별 종가로 사용할 수 있는 규칙을 확정한다.
- 같은 날짜의 행이 여러 개일 수 있는지, 조회구분에 따라 원본 의미가 달라지는지 확인한다. 일자당 한 봉으로 결정할 수 있을 때만 `(Symbol, TradeDate)` 키에 저장한다. 원본 일별 체결 데이터를 그대로 일봉 테이블에 덮어쓰지 않는다.
- 로컬 리소스에는 o3104 연속 키가 없고 현재 이벤트에도 `IsNext`가 없다. o3103의 페이지 처리 방식을 그대로 적용하지 않고, 조회일 기준 범위와 과거 조회 방식을 확인한다.
- 응답에 Symbol이 없으므로 요청 종목과 조회 조건을 요청 컨텍스트로 보관해 응답에 연결한다. 같은 o3104 TR 요청도 응답 전에는 덮어쓰지 않도록 직렬화한다.
- OHLC는 High >= Open, Close 및 Low <= Open, Close 조건을 만족시킨 다음 ScottPlot에 넘긴다. 0값 대체만으로 범위가 틀어지지 않게 한다.

### OVC: 실시간 체결

리소스 Res/OVC.res에는 계약코드, 현지/한국 날짜와 시간, 현재 체결가, 전일 대비, 등락률, 시가·고가·저가, 건별/누적 거래량, 체결방향 및 매수·매도 누적 체결량이 있다. 현재 OFutureRealDataService와 OFutureRealData가 이 필드를 읽고 있다.

추가로 리소스에는 장마감일 `ovsmkend`가 있으나 현재 서비스/모델에는 매핑이 없다. 거래일 판정에 필요한지 확인하고, 사용한다면 원문을 보존하는 모델 필드와 저장 필드를 함께 추가한다. 리소스 설명만으로 이를 봉의 거래일로 사용하지 않는다.

- 선택 계약을 바꾸면 이전 계약의 OVC 구독을 해제하고 새 계약을 구독한다.
- 현재 `Subscribe/Unsubscribe`는 OVC/OVH를 함께 처리한다. OVC 전용 시작/정지를 추가하고 기존 호출과의 호환성을 유지한다. 이번 소스에서 실시간 서비스를 호출하는 화면은 대시보드로 확인되지만, 이후 공유 시에는 계약별 소유자/참조 수를 관리해야 한다.
- OVC 이벤트는 UI Dispatcher 내부에서 현재 활성 화면·선택 계약·선택 세대를 다시 확인한 뒤 아래 실시간 정보 패널을 갱신한다. Dispatcher에 넘기기 전 검사만으로는 선택 변경 경쟁을 막을 수 없다.
- 새 계약의 `GetLatestTrade()`가 있으면 수신 시각과 함께 사용하되, 구독 자체가 새 체결이나 초기 시세를 보장하지는 않는다. 구독 해제 시 메모리 최신값도 삭제되므로 재진입은 DB 스냅샷을 우선 사용한다.
- 표시 시각은 현지 시간과 한국 시간을 구분한다. 원본 날짜/시간 문자열과 저장 시각을 혼동하지 않는다.
- DB에는 계약별 최신 OVC 스냅샷을 유지한다. 높은 체결 빈도로 DB를 매 틱 동기 저장하지 않도록 단일 쓰기 큐에서 최신값을 합치거나 짧은 주기로 일괄 upsert한다. 화면은 OVC 이벤트를 직접 받아 지연 없이 갱신하고, 재시작 시 DB 스냅샷을 초기 표시값으로 사용한다.
- 수신 시각은 COM 콜백에서 한 번 기록해 UI/저장소에 같이 전달한다. 구독 해제·앱 정상 종료 전 미저장 최신값을 저장 큐에서 비우고, 늦은 이전 스냅샷이 더 최신 행을 덮지 않게 한다. 비정상 종료 시 마지막 일괄 저장 이후 값은 유실될 수 있다.
- 이번 1차 구현은 OVC 하단 값 갱신과 스냅샷 저장을 대상으로 한다. 현재 코드의 `DateTime.Today` 기반 일봉 합성을 그대로 옮기지 않는다. OVC로 일봉/분봉을 실시간 합성하는 기능은 시장 거래일·봉 경계·중복 처리 규칙을 확정한 뒤 별도로 적용한다.

### 공통 요청 수명과 오류 처리

- 같은 TR에는 미완료 요청을 하나만 두고, 주식·해외선물 전체 공통 한도와 해당 TR의 응답 완료 대기를 모두 만족한 뒤 다음 요청을 보낸다. 큐 접수, 호출 한도 대기, 전송, 응답 수신, DB 저장 완료를 별도 상태로 관리한다.
- 요청 컨텍스트에 요청 식별자, 종목, 주기/조회구분/조회일, 연속 키를 보관한다. 아직 전송하지 않은 이전 선택의 중복 작업은 취소/병합하고, 전송한 요청의 컨텍스트는 응답 처리까지 유지한다.
- `Request()` 음수 반환, `ReceiveMessage`의 오류, 빈 정상 응답, 시간 초과, DB 저장 오류를 구분한다. 현재 조회 서비스는 `ReceiveData`만 연결하며, `IXAQueryService`/`XAQueryService`에는 메시지 핸들러 등록과 오류 조회 메서드가 이미 있다.
- 시간 초과 뒤 같은 Query의 입력만 바꿔 재사용하면 늦은 이전 응답을 새 요청으로 오인할 수 있다. 이전 인스턴스의 핸들러 해제·격리/재생성과 요청 세대 구분 등 복구 방식을 구현하고, 안전하게 구분할 수 없는 응답을 새 컨텍스트로 저장하지 않는다.
- `ProcessChartQueueAsync()`는 현재 `Task.Run`에서 COM Query를 사용한다. COM 객체 생성/호출/이벤트의 소유 스레드와 메시지 처리를 확인하고 요청 전용 Dispatcher 또는 적절한 STA 경계에서 다룬다. DB 작업을 백그라운드로 옮기는 것과 COM 호출을 옮기는 것을 구분한다.

## 5. 데이터베이스 설계 초안

기존 OFutureContracts는 사용자 관심계약 목록으로 유지한다. 거래소 전체 마스터를 DB에 넣지 않는다. EF Core 모델/키와 EnsureCreatedAndExtended()의 CREATE TABLE IF NOT EXISTS 보완을 함께 갱신한다.

### OFutureMinuteBars

| 필드 | 목적 |
|---|---|
| Symbol | 계약코드 |
| IntervalMinutes | 1 또는 10. 동일 시간의 서로 다른 주기를 구분 |
| TradeDate | API 날짜 원문 (yyyyMMdd) |
| TradeTime | API 현지시간 원문 (HHmmss) |
| Open, High, Low, Close | 분봉 가격 |
| Volume | 해당 봉 거래량 |
| ReceivedAtUtc | 해당 행을 마지막으로 API에서 받은 UTC 시각 |

복합 기본키는 (Symbol, IntervalMinutes, TradeDate, TradeTime)로 한다. 동일 봉을 다시 받은 경우 중복 삽입 대신 OHLCV와 ReceivedAtUtc를 갱신한다. 시간은 거래소/한국 시간대를 잘못 변환하지 않도록 API가 준 문자열을 보존하고, 정렬 키를 일관되게 사용한다.

`Date`/`Time`이 각각 유효한 `yyyyMMdd`/`HHmmss`인지 확인한다. `TimeDifference` 같은 응답 단위 정보는 필요한 경우 행 또는 별도 조회 메타데이터로 보존한다. 수신 시각을 DB 쓰기 시각으로 대체하지 않는다.

### OFutureDailyBars

| 필드 | 목적 |
|---|---|
| Symbol, TradeDate | 계약코드와 일자, 복합 기본키 |
| Open, High, Low, Close | 일봉 가격 |
| Volume | 일 거래량 |
| Change, ChangeRate, Sign | 화면 정보/디버깅/일별 값 비교 |
| ReceivedAtUtc | 최신화 시각 |

이 테이블은 **정규화한 일봉**을 저장한다. 현재는 명시적 OHLC 필드가 있는 o3108 응답만 저장한다. o3104는 `gubun="0"` 일별 체결 결과를 별도 캐시에 보관하지만, 화면의 `price`가 날짜별 종가인지 확인되기 전까지 일봉으로 투영하지 않는다. 향후 원천을 바꿀 때는 `SourceTrCode`와 조회구분을 저장하고 기존 원천의 값을 기준 없이 섞어 덮어쓰지 않는다.

### OFutureLatestQuotes

| 필드 | 목적 |
|---|---|
| Symbol | 계약코드, 기본키 |
| Price, Change, ChangeRate, ChangeSign | OVC 최신 체결 |
| Open, High, Low | 당일 실시간 OHLC |
| TradeQuantity, TotalQuantity | 건별/누적 거래량 |
| TradeDirection, SellTradeQuantity, BuyTradeQuantity | 체결 방향/매도·매수 누적량 |
| OverseasDate, TradeTime, KoreaDate, KoreaTradeTime | API 원본 시각 |
| MarketEndDate (필요 시) | `ovsmkend` 원문. 의미 확인 후 추가 |
| ReceivedAtUtc | COM 콜백에서 기록한 수신 UTC 시각 |
| StoredAtUtc | 일괄 upsert가 DB에 반영된 UTC 시각 |

이 테이블은 계약별 최신 스냅샷 한 행을 갱신한다. 수신/저장 시각을 구분해 표시하고, 캐시 로드·수신 정지·연결 끊김·마지막 수신 후 기준 시간 경과는 실시간 확인 전 상태(stale)로 표시한다. 새 체결을 받으면 현재 연결/구독 상태와 수신 시각을 기준으로 재평가한다. DB 로드가 늦게 완료되어도 이미 표시한 새 OVC 값을 덮지 않게 한다.

### 저장소 경계와 동시성

- 저장소는 읽기, 분봉 upsert, 일봉 upsert, 최신 OVC 스냅샷 upsert를 제공한다.
- `App.xaml.cs`에는 `AddDbContextFactory<DumbTraderDbContext>()`가 이미 등록되어 있다. 이를 저장 서비스에 주입하고 작업별로 새 Context를 생성/해제한다. 기존 싱글턴 Context는 관심계약 기능 등이 사용하므로 새 저장소의 작업 스레드와 공유하지 않는다.
- DB 작업은 UI/COM 콜백 밖에서 실행하며 쓰기는 직렬화한다. 새 Context를 만드는 것만으로 UI 차단이 해결되는 것은 아니므로, 읽기/upsert 실행 경계도 함께 정한다. 관심계약 저장 등 기존 쓰기와의 SQLite 잠금 경합도 확인한다.
- 이벤트 데이터는 저장 큐에 넣기 전 복사하고, 저장 큐의 크기/오류 상태를 관리한다. OVC는 계약별 최신값을 합치되 조회 페이지는 유실하지 않는다. 저장 실패 시 ‘최신화 완료’로 표시하지 않고 기존 DB 데이터를 유지한다.
- 복합 기본키가 계약/주기/시간순 조회를 지원하는지 확인하고 필요한 인덱스만 추가한다. 새 DB의 EF 모델과 기존 DB용 CREATE TABLE/INDEX가 같은 키·열·형식을 갖도록 한다. `EnsureCreated()`만으로 기존 DB에 새 테이블/인덱스가 추가되지는 않는다.
- 과거 차트 행을 자동 삭제할 보존 기간은 이번 요구에 없다. 기본 구현은 날짜 키로 누적하고, 보존 정책이 필요하면 별도 결정으로 둔다.

## 6. 화면 및 상태 설계

### XAML 배치

1. 루트 Grid의 왼쪽 열을 관심계약 영역, 오른쪽 열을 대시보드 영역으로 나눈다.
2. 왼쪽 영역에 OFutureDetailView.xaml의 제목과 읽기 전용 DataGrid 스타일/바인딩 구조를 가져온다.
3. 오른쪽 Grid를 차트 상단과 OVC 하단으로 나눈다.
4. 차트 상단 Grid는 2열·2행으로 구성한다.
   - 일봉: 첫 열/첫 행
   - 10분봉: 첫 열/둘째 행
   - 1분봉: 둘째 열을 두 행에 걸쳐 표시
5. OVC 실시간 패널은 오른쪽 전체 폭을 사용한다.
6. OFutureDashboardView.xaml의 카드 WrapPanel과 카드 데이터 템플릿을 제거하고, 기존 리소스 브러시와 제목/테두리 스타일을 사용한다. 기존 카드 Control/ViewModel 파일의 삭제는 필요하지 않다.
7. 현재와 같이 ViewModel이 `WpfPlot`을 소유한다면 `DailyPlotControl`, `TenMinutePlotControl`, `OneMinutePlotControl` 세 인스턴스를 만들고 XAML `ContentControl.Content`에 각각 바인딩한다. XAML에 같은 차트를 중복 생성하지 않는다.
8. 세 차트의 축 상태를 독립 관리하고, OVC 패널 갱신이나 같은 계약의 추가 조회 때문에 사용자의 확대·이동 범위가 매번 초기화되지 않게 한다. 선택 변경 시에는 해당 계약의 기본 범위를 적용한다.

### ViewModel

SelectedOFutureCard 대신 SelectedOFutureContract를 중심 상태로 둔다. 관심계약 ObservableCollection<OFutureContract>, 세 차트 데이터/PlotControl, OVC 최신값, 차트별 조회·저장 상태, OVC 수신 상태와 수신/저장 시각을 제공한다. 초기에는 첫 관심계약을 선택하고, 목록 갱신 시 같은 Symbol의 선택을 유지한다. 선택 계약이 삭제되면 첫 계약으로 이동하며 빈 목록이면 선택을 해제한다.

선택 변경 시 아래 순서를 따른다.

1. 선택 세대를 증가시키고 이전 선택의 미전송 요청/DB 로드를 취소하거나 무효화한다. 이전 계약의 소유한 OVC 구독을 해제하되 이미 수신한 미저장 최신값은 저장 큐에 유지한다.
2. 새 계약이 없으면 차트와 OVC 패널을 초기 안내 상태로 바꾼다.
3. 새 계약의 DB 일봉·1분봉·10분봉 데이터를 읽어 각 차트를 즉시 표시한다.
4. DB에 저장된 최신 OVC 스냅샷을 표시하되 저장 시각을 붙여 API 수신 전 데이터임을 드러낸다.
5. 활성 화면에서 새 계약 OVC 구독을 시작하고 수신 상태를 표시한다. 기존 수신 정지 명령과의 관계는 아래 화면 수명 규칙을 따른다.
6. o3103 1분/10분과 o3108 일봉 요청을 공통 작업 큐에 넣는다. 주식·해외선물 TR이 공유하는 초당/10분 한도를 함께 지킨다. o3104는 API 의미가 검증되기 전까지 대시보드 요청에서 제외한다.
7. 각 응답은 보존한 요청 컨텍스트와 종목/주기를 확인한다. 이미 전송된 이전 선택의 정상 응답은 원래 계약의 DB에 저장하되 현재 화면은 갱신하지 않는다. 안전하게 매칭할 수 없는 응답은 저장하지 않고 오류로 처리한다.
8. DB upsert 완료 후 해당 차트 데이터를 다시 읽거나 해당 봉만 반영한다. 모든 비동기 DB 결과와 Dispatcher 실행 내부에서 활성 화면·Symbol·선택 세대를 재검사한다. A→B→A 선택에서도 이전 A의 작업이 새 A 화면을 덮지 않게 한다.

### 선택과 화면 수명

OFutureDashboardViewModel은 현재 싱글턴이다. `MainViewModel`은 메뉴 진입마다 View를 새로 만들지만 같은 ViewModel을 다시 연결한다. 현재 대시보드에는 화면 이탈 시 정리 코드가 없으므로 수신이 계속될 수 있다.

- `Activate/Deactivate` 같은 재호출 가능한 경계를 Loaded/Unloaded에 연결하고 중복 활성화를 막는다. 서비스 이벤트를 생성자에서 한 번 연결하고 활성 여부로 차단하거나, 활성화마다 정확히 한 번 연결/해제하는 방법 중 하나로 통일한다.
- 첫 진입은 계획의 자동 구독 흐름을 따르되 수신 시작/정지 버튼을 유지한다. 사용자가 정지한 상태는 선택 변경/재진입으로 자동 해제하지 않고, 시작 버튼을 누르면 현재 선택만 구독한다. 화면 이탈은 실제 구독을 해제하며, 재진입은 보관한 사용자 수신 의도에 따라 복원한다.
- 생성자에서 첫 카드를 선택하며 시작하는 기존 차트 요청을 활성화 흐름으로 옮겨, Loaded에서 같은 요청을 중복 전송하지 않는다. 비활성 동안 관심계약이 바뀌면 재진입 시 목록과 선택을 서비스 상태에 맞춰 동기화한다.
- 일시 이탈에서는 비활성화하고, 싱글턴 ViewModel의 영구 Dispose는 앱 종료 시 수행한다. DB 저장 큐는 화면보다 긴 수명을 갖고 마지막 미저장 스냅샷을 정상 종료 시 반영한다.

## 7. 단계별 작업 계획

### 1단계: API 의미와 저장 키 확정

- Res/o3103.res, Res/o3104.res, Res/OVC.res의 필드와 이벤트를 대조한다.
- 첨부 설명의 o3104 조회구분(`0` 일별 / `1` 주별 / `2` 월별)과 주식·해외선물 전체 합산 한도(초당 1건 / 10분당 200건)를 구현 명세에 반영한다. 조회일자 범위와 price의 일봉 종가 사용 가능성은 Xing 문서 또는 실제 응답으로 확인한다.
- o3103 연속조회 종료 판정, 1분/10분 요청 순서와 앱 공통 대기열 처리 방식을 정한다.
- 현지 날짜·시간과 한국 날짜·시간의 사용 규칙, 중복 봉 식별키를 확정한다.
- 결정 결과를 API 요청 주석과 모델에 반영한다.
- o3104가 일자별 OHLC를 보장하는지 확인하고 원천 TR·종가 매핑·일봉 자연키를 확정한다. 확인 전에는 해당 일봉 저장/표시 작업을 완료로 처리하지 않는다.
- 초기 조회 기간, 페이지/봉 수 상한, 부분 수집 표시와 타임아웃 뒤 늦은 응답의 격리 방식을 정한다.

완료 조건: 필요한 입력값, 필드 매핑, DB 자연키, 재조회 범위와 일봉 데이터 원천이 관련 저장/조회 구현 전에 명시되어 있다. 로컬 RES만으로 확인되지 않은 API 의미를 확정 사항으로 표시하지 않는다.

### 2단계: SQLite 영속화 추가

- 분봉·일봉·최신 OVC 모델을 추가한다.
- 복합키와 필요한 조회 인덱스를 설정한다. 일봉 키는 1단계의 의미 확인 결과를 따른다.
- DumbTraderDbContext DbSet과 OnModelCreating을 추가한다.
- 기존 DB를 위한 안전한 테이블 생성을 EnsureCreatedAndExtended()에 추가한다.
- DbContext Factory를 사용하는 OFutureChartStoreService를 만들고 읽기/upsert API를 제공한다.
- 이미 등록된 DbContext Factory를 재사용하고 저장 서비스를 DI에 등록한다. 수신/저장 시각, 직렬 쓰기, 종료 시 잔여 OVC 저장을 구현한다.
- 재시작 후 읽기, 중복 행 갱신, 기존 관심계약 보존을 확인한다.

완료 조건: 기존 SQLite 파일을 삭제하지 않고 새 테이블이 생성되며, 동일 자연키 재수신 시 행 수가 증가하지 않고 최신 값이 갱신된다.

### 3단계: API 응답 저장과 요청 직렬화

- o3103 요청을 1분/10분 큐 항목으로 식별하고, 한 번에 한 요청만 보낸다.
- 응답 컨텍스트에 계약코드와 ncnt를 보존해 이벤트의 분봉과 원요청을 매칭한다.
- `IsNext`와 유효한 연속 키가 있으면 백필 상한까지 페이지를 이어 받는다. 빈/반복 페이지와 반복 키에서 중단하며 마지막 페이지로 기존 누적 데이터를 대체하지 않는다.
- o3104도 같은 TR 인스턴스에 중복 요청하지 않게 하고 응답 종목/조회일을 매칭한다.
- o3104 gubun 입력은 `"0"`/`"1"`/`"2"`로 검증한다. 대시보드의 o3104 호출은 조회 범위와 `price`의 종가 의미가 확인된 뒤에만 추가하며, 그때 일별 요청은 `"0"`을 지정한다. 미지원 값은 전송 전에 거절하고 요청 컨텍스트의 조회구분을 저장 경로까지 유지한다.
- 싱글턴 `XingTrQuerySchedulerService`에 주식·해외선물 TR 전체 전송 간격 1초와 최근 600초 합계 200건 상한을 적용한다. 현재 주식 데이터(t1101/t8407/t8410/t8430), 계좌/주문 및 해외선물(o3101/o3103/o3104/o3105/o3106/o3107/o3108 포함) 전송 경로를 공통화한다.
- 주식 차트 전용 큐와 직접 전송 경로를 공통 스케줄러에 통합하고, 관심계약 관리의 o3101 자동/수동 조회와 상세 화면의 o3108 호출을 회귀 확인한다. 공통 제한을 우회하는 직접 호출 경로를 남기지 않는다.
- 각 응답을 필드 검증한 후 저장소에 upsert한다. 차트의 일봉 원천은 검증된 OHLC가 있는 o3108이며 o3104 `price`를 종가로 추정하지 않는다. 숫자 파싱 실패는 NaN/센티널로 구분하고, 유효한 범위의 OHLC와 날짜·시간만 차트 캐시/DB에 넣는다. 음수 가격을 무조건 오류로 처리하지 않는다.
- 요청 거절, API 오류, 빈 응답, 시간 초과를 화면의 상태와 로그에 구분해 노출한다.
- 메시지 이벤트와 요청별 완료/오류 상태를 연결한다. 시간 초과 후 재시도는 이전 응답이 새 컨텍스트로 매칭되지 않게 하며, COM 소유 스레드에서 요청을 실행한다.
- 선택 계약이 바뀐 뒤 늦게 도착한 응답도 계약별 DB 데이터는 저장하되 이전 계약 데이터가 새 선택 차트를 덮지 않게 한다.

완료 조건: 1분·10분·일봉 요청을 연속 수행해도 결과가 올바른 심볼/주기/날짜에 저장된다.

### 4단계: 관심계약 왼쪽 목록과 차트 화면

- OFutureDashboardView.xaml을 첨부 레이아웃으로 재구성한다.
- 상세 화면의 관심계약 DataGrid를 대시보드에 연결한다.
- SelectedOFutureContract 전환 시 3개 차트 데이터를 DB에서 먼저 로드한다.
- 각 차트는 ScottPlot 캔들에 올바른 날짜 라벨과 축 범위를 설정한다.
- 데이터가 없거나 API 연결이 끊긴 경우 빈 상태/마지막 저장 시각을 표시한다.
- 창 크기 변경, 긴 계약명, 빈 관심목록, 미선택 상태를 시각 확인한다.
- 비동기 DB 읽기/차트 갱신 시 선택 세대를 확인하고, Dispatcher 내부에서도 현재 선택을 확인한다. 첫 선택·삭제 후 대체 선택·화면 재진입을 같은 활성화 흐름으로 처리한다.

완료 조건: 관심계약 선택에 따라 일봉·10분봉·1분봉이 모두 같은 종목으로 바뀌고 저장 데이터가 먼저 표시된다.

### 5단계: OVC 실시간 하단 패널

- 선택 계약 OVC만 구독하고 선택 변경 시 구독 대상을 교체한다.
- 현재 OVC/OVH 결합 구독을 분리하고 기존 서비스 호출과의 호환성을 확인한다.
- 수신 이벤트를 Dispatcher로 넘겨 값 패널을 갱신한다.
- OVC 최신 스냅샷 저장을 쓰기 큐에서 coalesce/upsert한다.
- DB 스냅샷을 앱/화면 재시작 시 우선 표시하고 수신/저장 시각과 stale 상태를 보여준다. 새 실시간 값이 들어온 뒤 완료된 DB 읽기는 이를 덮지 않는다.
- 수신 정지·화면 이탈·재진입 시 구독 및 이벤트 중복을 확인한다.
- 수신 정지 의도를 선택 변경/재진입에서도 유지하고, 연결 끊김 시 상태를 갱신한다. 정상 종료 직전 마지막 스냅샷의 저장을 확인한다.

완료 조건: 선택 계약 실시간 체결만 표시되고, 다른 종목의 이벤트가 패널 값을 바꾸지 않으며, 화면 재진입 시 구독과 갱신이 한 번씩만 동작한다.

### 6단계: 검증과 인수

- 기존 관심계약 추가/삭제/재시작 지속성에 회귀가 없는지 확인한다.
- 1분봉·10분봉 동시 요청 및 연속 응답에서 필드가 섞이지 않는지 검증한다.
- 요청 완료보다 빠른 A→B→A 선택, DB 로드 지연, Dispatcher 대기 중 선택 변경, 타임아웃 후 늦은 응답과 재시도를 검증한다.
- 빈 결과, 중복 응답, 0 OHLC, Low > Open/Close, 시간대 변경, 재접속 응답을 확인한다.
- API 성공 뒤 DB를 닫았다 다시 열어 마지막 캔들과 OVC 스냅샷이 보이는지 확인한다.
- 실시간 수신률에서 UI가 멈추지 않는지, SQLite 잠금·쓰기 지연·누적 DB 크기를 확인한다.
- 새 DB와 기존 DB 사본에서 스키마/인덱스가 같고 기존 관심계약이 보존되는지 확인한다. 저장 실패/정상 종료 직전 미저장 값/이전 스냅샷의 지연 저장도 검증한다.
- `DumbTrader.csproj`의 대상은 `net9.0-windows`, `UseWPF=true`, `PlatformTarget=x86`이며 Xing COM 참조를 사용한다. Visual Studio 2022의 .NET Framework MSBuild로 솔루션을 빌드한다. `dotnet build`만으로 COM 참조 검증을 대신하지 않는다.

## 8. 검증 시나리오와 수용 기준

1. 관심계약 두 개 이상을 DB에 보관한 뒤 대시보드에 진입한다. 왼쪽 목록에 저장된 계약이 표시된다.
2. 첫 계약을 선택한다. 해당 계약의 저장된 차트가 우선 표시되고, DB가 비어 있으면 빈 상태가 표시된다.
3. API 응답 후 1분·10분·일봉이 각각 올바른 계약과 주기로 저장되고 표시된다.
4. 같은 응답을 재수신해도 자연키가 같은 기존 행을 갱신한다.
5. 다른 계약을 선택한다. 세 차트와 OVC 패널 모두 새 계약 기준으로 바뀌며 이전 계약의 늦은 응답이 화면에 섞이지 않는다.
6. OVC 이벤트가 들어오면 체결가·시각·누적량 등이 UI 응답성을 해치지 않고 갱신된다.
7. 앱을 재시작해 첫 선택계약의 DB 차트와 마지막 OVC 값이 우선 표시되고, 새 체결 수신 시 상태가 최신화된다. 마지막 선택계약의 앱 재시작 간 영속화는 이번 범위에 없으며 화면 재진입 시에는 선택을 유지한다.
8. High >= max(Open, Close) 및 Low <= min(Open, Close)가 모든 ScottPlot OHLC 입력에서 성립한다.
9. 화면을 여러 번 나갔다 들어와도 OVC 이벤트 핸들러나 구독이 중복되지 않는다.
10. 수신 정지 후 선택을 바꾸거나 재진입해도 자동 재구독되지 않으며, 시작 버튼은 현재 선택만 구독한다. OVC 전용 수신으로 불필요한 OVH 구독이 생기지 않는다.
11. A→B→A 선택, 지연된 DB 읽기/Dispatcher 작업, 타임아웃 후 늦은 응답이 현재 선택의 차트·체결값을 덮지 않는다. 매칭할 수 없는 응답은 잘못된 키로 저장되지 않는다.
12. 여러 분봉 페이지를 받은 뒤 DB에는 앞 페이지가 유지되며 반복 키/빈 페이지/백필 상한에서 요청이 종료된다. 부분 수집·오류·저장 완료를 화면에서 구분한다.
13. 정상 종료 직전 합쳐둔 최신 OVC 값이 DB에 반영되고, 오래된 저장 작업이나 DB 초기 로드가 더 최신 값을 되돌리지 않는다. 수신 정지/연결 끊김/캐시 상태가 시각과 함께 표시된다.
14. 기존 상세 화면의 o3108 일봉 조회와 관심계약 관리 진입 시 전체 마스터 자동 조회·수동 새로고침이 유지된다. 전체 마스터가 DB에 저장되지 않는다.
15. o3104 서비스는 `"0"`/`"1"`/`"2"`만 허용하고 미지원 구분값을 거절한다. 현재 대시보드는 o3104를 요청하지 않으며 일봉은 o3108에서 가져온다. o3104를 추후 호출할 때 주별/월별 응답이 일봉 캐시·테이블에 섞이지 않고, 일별 응답은 의미 확인 뒤에만 일봉으로 투영한다.
16. 시간/전송을 대체한 검증에서 주식 TR과 서로 다른 o31XX 코드 사이에도 전송 간격이 1초 미만이 되지 않는다. 주식 t8410 100회와 o3108 100회 등 최근 600초 합계가 200건이면 다음 o3104 또는 주식 TR이 대기한다. TR 코드별 요청 수가 200건 미만이어도 총량 한도를 우회하지 못한다.
17. 관심계약 관리의 o3101, 주식 시세/차트/종목 조회, 계좌/주문 TR, 상세 화면의 o3108, 연속조회 페이지와 재시도도 같은 예산을 사용한다. 화면 전환·Query 재생성으로 예산이 초기화되지 않고 허용 시각 이후에만 전송이 재개된다. 한도 대기 중 응답 타임아웃이 발생하지 않으며, 전송 전 취소한 작업은 호출 수에 포함하지 않는다.
18. 계약별 해외선물 주전략 설정은 앱 재시작 뒤 복원된다. 실시간 OVC 입력은 BUY/SELL/HOLD 신호로만 표시되며 주문 TR을 호출하지 않는다.
19. 시뮬레이션은 기간 전 저장 봉으로 지표를 준비하고 선택 기간 안에서만 거래한다. 종가 신호는 다음 봉 시가에 적용하고 틱 가치·개시증거금·최대 계약 수를 사용한다. 저장 봉이나 계약 메타데이터가 부족하면 실행을 거절하고 원인을 표시한다.
20. 전략이 미설정/준비/신호/실행 오류 상태인지 대시보드에서 구분할 수 있다. 전략 스크립트 실행 오류는 숨기지 않고 이유를 표시하며, BUY/SELL 신호도 주문 미전송임을 함께 표시한다.

## 10. 범위 경계와 미확정 항목

### 이번 작업에 포함

- 대시보드 레이아웃 교체
- 관심계약 선택과 선택 계약 차트 표시
- o3103의 1분/10분 조회, o3108 일봉 조회. o3104 대시보드 조회는 의미 확인 후 별도 반영
- o3104 조회구분 검증(`0/1/2`). 대시보드 일별 `"0"` 호출은 `price`의 종가 의미와 조회 범위를 확인한 뒤 별도 반영
- 모든 주식·해외선물 일반 TR 호출이 공유하는 초당 1건·10분당 합계 200건 제한과 공통 요청 스케줄러
- o3104 일봉 사용 가능성 확인과 기존 o3108 원천과의 전환 판단
- 조회 데이터의 SQLite 저장 및 DB 우선 표시
- 선택계약 OVC 실시간 값 표시와 최신 스냅샷 저장
- OVC/OVH 구독 분리, 화면 활성화/비활성화와 수신 시작/정지 상태 관리
- 주식 Roslyn 구조에 기반한 해외선물 계약별 신호 전략과 저장 봉 기반 일봉/1분/10분 시뮬레이션. 실시간은 신호 표시 전용이며 주문 자동 제출은 하지 않음

### 이번 1차 구현에서 제외

- 이미지에 적힌 보조지표·오버레이 지표 계산/표시
- OVC 틱으로 현재 일봉·1분봉·10분봉을 실시간 합성하는 기능. 1차 기본안은 하단 OVC 값만 실시간 갱신하며, 기존 일봉 합성 동작의 변경도 인수 시 확인한다.
- 전체 거래소 마스터의 DB 저장, 마지막 선택계약/수신 정지 의도의 앱 재시작 간 영속화
- 사용자 데이터 자동 삭제와 보존기간 정책 변경
- o3104 주별(`"1"`)/월별(`"2"`) 차트 UI와 해당 주기 데이터의 영속화

### 전략 및 시뮬레이션 범위

- 주식의 Roslyn `main` 스크립트 실행 패턴을 참고하되, 해외선물은 `strategy/ofuture/main` 스크립트와 별도 계약별 설정 파일 및 실행 컨텍스트를 사용한다.
- 실시간 전략은 현재 선택 계약의 OVC 수신값으로 BUY/SELL/HOLD 신호를 표시한다. 자동 주문은 보내지 않는다.
- 시뮬레이션은 SQLite에 저장된 o3108 일봉 또는 o3103 1분/10분 봉을 입력으로 사용한다. 시작일 이전 봉도 지표 준비에 쓰지만 거래에는 포함하지 않는다.
- 봉 종가에서 나온 신호는 다음 봉 시가에 적용한다. 손익은 계약의 TickSize/TickValue, 진입 수량은 OpeningMargin 및 사용자가 지정한 최대 계약 수로 제한한다. 결과 통화는 계약 통화다.
- 시뮬레이션 계약 메타데이터는 로컬 `Res/o3101.res`의 `UntPrc`(호가단위가격), `MnChgAmt`(최소가격변동금액), `OpngMgn`(개시증거금)을 모델에 매핑한다. 필수 값이 0 이하이면 손익을 추정하지 않고 실행을 거절한다.
- 기본 이동평균 교차 전략은 예제로만 제공한다. 수수료·슬리피지·환전 및 만기 연속 보정은 범위 밖이며, 미청산 포지션의 평가손익은 별도 표시한다.

### 별도 결정이 필요한 항목

- o3104 조회일의 범위/시장 날짜 기준, 날짜별 데이터 의미, 일봉 종가로 사용할 필드 및 일봉 자연키. 검증되지 않으면 o3108 유지 여부. gubun의 코드 의미는 첨부 설명으로 확인 완료
- 화면에서 원하는 일봉/분봉 과거 조회 기간 및 자동 백필 상한
- 공통 한도 내 재시도 간격과 전송 우선순위, 서버의 기간 경계 처리. 주식·해외선물 전체 합산 한도(초당 1건·10분당 200건)는 사용자 설명으로 확정했으며 미확정 항목으로 남기지 않음
- 현지 날짜·시차·장마감일과 시장 거래일의 관계. 후속 실시간 봉 합성 범위와 규칙
- OVC 저장 coalesce 간격과 stale 경고 기준
- DB 보존기간, 오래된 분봉 정리 여부

미확정 API 값은 Xing 문서/실응답으로 확인한 후 코드에 반영한다. 조회 범위·저장 간격·stale 기준은 명시적인 구현 설정으로 정하고, 보존 정책은 사용자 요구와 실제 용량 확인 후 별도 결정한다.

## 11. 이번 검토 결과와 검증 범위

- 현재 구현은 대시보드 레이아웃/선택 계약 차트, o3103/o3108 요청과 SQLite 차트 저장, OVC 전용 구독과 최신 스냅샷 복원/주기 저장을 포함한다. o3104 서비스의 일별 조회·캐시·구분값 검증은 남아 있지만, `price`의 날짜별 의미가 확인되지 않아 대시보드에서는 요청하지 않고 일봉 종가로도 쓰지 않는다. 일봉 원천은 o3108이다.
- 주식 `t8410` 단독 큐 외에 t1101/t8407/t8430, 계좌·주문 TR까지 우회 경로가 있던 점을 확인했다. 이를 `XingTrQuerySchedulerService` 싱글턴으로 묶어 주식·해외선물 일반 TR을 공유 제한하고, 응답 처리까지 같은 TR 요청을 직렬화하도록 연결했다. 실시간 구독 이벤트는 이 요청 한도에 포함하지 않는다.
- 스케줄러 대기 취소, 요청별 응답 시간 초과, 서버 시스템 오류 후 Query 교체와 인스턴스 기반 늦은 응답 차단을 해외선물 조회, 주식 조회, 계좌·주문 TR에 연결했다. 선택 변경/화면 이탈 때 대시보드 요청을 취소한다. 앱 종료 시 OVC 잔여 스냅샷 flush도 추가했으나, 종료 직전 강제 종료·실제 COM 응답 시나리오는 런타임 검증이 남아 있다.
- 공통 스케줄러 상태를 대시보드에 연결했다. 요청 대기열 등록, 같은 TR 응답 대기, 호출 한도 대기, 전송 중, API 응답 수신, DB 저장 완료/실패를 구분해 표시한다. 이 상태 변경은 선택된 계약의 o3103/o3108 요청에 한해 화면에 반영한다.
- 11-06 기준선에는 당시 일봉 원천(o3108), 상세 화면의 실제 조회 주기(일봉), o3103/o3104의 미연결 상태, 캐시 동작을 기록했다. 이후 구현에서 대시보드의 o3103/o3108 요청 연결과 저장이 추가됐다.
- 주식 차트 전용 전송 큐와 해외선물 TR 직접 전송을 싱글턴 공통 스케줄러로 묶었다. 주식·해외선물 데이터, 계좌, 주문 TR 모두 같은 대기열과 합산 예산을 사용한다. 전체 요청은 초당 1건, 최근 600초의 호출 시도 최대 200건이며, 대기 중인 호출에는 응답 타임아웃을 적용하지 않는다. Query 호출/교체는 소유 Dispatcher에서 실행하고, 서비스별 Query 교체와 이전 인스턴스 응답 차단을 연결했다.
- 대시보드 OVC 전용 구독과 화면 수명을 연결했다. OVC 표시값을 일봉으로 합성하던 동작을 제거하고 o3108 일봉 OHLC를 사용한다. 연결·구독·stale·마지막 수신/저장 시각을 표시한다.
- DB Factory 기존 등록을 반영하고 수신 시각/저장 시각 구분, 기존 DB 확장, 직렬 쓰기, 앱 종료 시 OVC 저장 flush와 오래된 결과의 역전 방지를 보완했다.
- 사용자 제공 o3104 설명 이미지를 문서 옆에 보관하고 조회구분 `0/1/2`를 반영했다. 서비스는 이 값을 검증하지만 대시보드는 현재 o3104를 요청하지 않는다. 일봉은 o3108을 사용하며, o3104 전환은 `price`와 조회 범위의 의미 확인 뒤 결정한다.
- 사용자 설명에 따라 호출 제한 범위를 **주식·해외선물 TR 전체 공유 한도**로 확장했다. 초당 1건·10분당 합계 200건을 모든 화면/조회 코드/계좌/주문/연속조회/재시도가 같은 앱 싱글턴 스케줄러에서 지키도록 구현과 수용 기준을 갱신했다.
- 전송 직전 XAQuery의 TR별 속도/기준 시간 및 요청/한도 카운터를 읽어 진단 로그에 남기고, 보고된 초당/기준초 제한과 요청 제한이 더 엄격할 때 추가 대기하도록 보완했다. 이 보조 제한은 전역 공통 한도를 완화하지 않는다.
- 주식 Roslyn 전략 패턴을 참조해 해외선물 전용 계약별 전략 서비스, 신호용 컨텍스트, 샘플 이동평균 교차 전략과 상세 화면 설정/시뮬레이션 UI를 추가했다. 저장된 일봉/1분/10분 봉을 재생하며 다음 봉 시가 체결, 틱 가치 손익, 개시증거금 기반 진입 수량 제한을 적용한다. 실시간은 신호 표시 전용이고 주문을 전송하지 않는다.
- A→B→A 선택에서 같은 계약의 이전 요청이 새 선택 화면을 갱신하지 않도록 선택 세대 번호를 분봉 연속조회 전체와 일봉 응답에 전달하고 Dispatcher 반영 직전에 검사한다. 이미 전송된 응답의 해당 계약별 DB 저장은 유지한다.
- 사용자 제공 설명 이미지의 조회구분 코드와 TR/블록 속성(Header `A`, Attribute `O`, Block Mode `O`, TR 크기 `118`, input `17`, output `101`, output `OCCURS`)을 계획에 기록했다. 크기 값은 표시 정보로만 기록하고 행 수나 전송 수로 해석하지 않는다.
- Visual Studio 2022 .NET Framework MSBuild 전체 빌드는 통과했다. WPF 실화면·Xing 연결 및 응답·기존 DB의 실행 중 업그레이드는 아직 검증하지 않았다. o3104 `price`의 날짜별 의미와 조회일 범위도 실응답/API 가이드에서 확인해야 한다.
- 전략/시뮬레이션을 연결한 뒤 Visual Studio 2022 MSBuild 전체 빌드도 통과했다. 남은 확인은 WPF 화면에서의 바인딩/사용성, 실제 Xing OVC 입력과 계약 메타데이터, 저장 이력 기반 시뮬레이션 결과 검토다. 빌드 성공은 전략 수익성이나 실거래 적합성 검증을 뜻하지 않는다.
- 사용자가 2026-11-07 직접 확인한 항목: 대시보드에 일봉·10분봉·1분봉 및 OVC가 표시되고, 저장 봉 기반 일봉·1분봉·10분봉 시뮬레이션 결과도 표시됨. TR 진단 로그와 공통 요청 제한은 이상 없음. 실시간 전략 신호 표시/주문 미전송 여부는 확인하지 못함.
- 신호 확인이 어렵던 원인은 전략 미설정 시 대시보드가 일반 대기 문구만 보이고, 스크립트 파일 누락/실행 실패를 신호 영역에 표시하지 않았다는 점이다. 상태 표시를 미설정·준비·신호·오류로 나누고 실행 오류 설명을 노출하도록 보완했다. 계약 선택 세대를 함께 확인해 이전 선택의 늦은 전략 결과가 현재 카드에 덮이지 않게 했다.
- 남은 사용자 확인은 관심계약의 상세 화면에서 주전략을 지정한 뒤 대시보드로 돌아와 `전략 준비됨` 또는 OVC 수신 후 신호/구체적인 스크립트 오류 문구가 나타나는지 보는 것이다. BUY/SELL은 신호 전용이며 자동 주문은 제출하지 않는다.
- 1분봉·10분봉은 일봉과 같이 보이는 구간의 고저가로 세로축을 자동 조정한다. 드래그 이동은 가로축만 변경하도록 잠그고, 데이터 범위 밖으로 벗어나지 않도록 제한한다. 분봉 시간 누락/거래 세션 공백은 연속된 표시 슬롯으로 압축해 봉을 빈 공간 없이 나란히 표시하되, 축 라벨은 원래 체결 시각을 사용한다.
- 분봉 위쪽 기간 선택 버튼(오늘/최근 1주/최근 1개월/전체)을 제공한다. 같은 선택 기간을 1분봉과 10분봉에 함께 적용한다. 선택은 이미 저장·수신한 봉의 표시 범위만 바꾸며 TR 요청을 추가하지 않는다. 초기 선택은 오늘이며 기간 변경 때 해당 데이터의 가시 범위에 맞춰 두 차트를 다시 맞춘다.
- 분봉 세로축 여백은 가격 절대값 비율이 아니라 현재 표시 구간의 고저 범위에 비례해 계산한다. 표시 봉의 가격이 거의 움직이지 않을 때는 계약 TickSize를 우선 사용해 평평한 차트와 0 높이 축 범위를 함께 방지한다.
- 로그는 읽기 전용 선택 가능한 텍스트로 표시하고 전체 복사 버튼을 제공한다. Xing `Request` 음수 반환에는 TR 코드·오류 코드·오류 메시지를 함께 남기며, 초당 전송 제한은 경계 경쟁을 피하도록 1.1초 간격으로 적용한다.
