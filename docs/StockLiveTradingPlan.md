# 국내주식 전략 신호 기반 실주문 개발 계획

## 1. 목표와 첫 배포 범위

국내주식 전략의 매수·매도 신호를 선택한 계좌의 Xing 현물 주문으로 연결한다. 화면에서는 전략 판단, 주문 접수, 부분 체결, 전량 체결, 취소, 거부를 구분한다. 차트의 실체결 마커와 보유 수량은 증권사가 확인한 체결로 갱신한다.

첫 배포 범위는 **지정가 현금 매수와 보유 주식 매도**다. 신용, 공매도, 시장가 전환 및 자동 정정은 후속 범위로 둔다. 실주문은 기본 비활성화하며, 로그인 세션마다 계좌·전략·종목·주문 한도를 확인한 뒤 명시적으로 활성화한다. 계좌 변경, 연결 종료, 앱 재시작으로 활성화가 해제된다.

## 2. 현재 코드와 연결 지점

| 기존 경로 | 구현 방향 |
| --- | --- |
| `StockDashboardViewModel` → `StrategyService.RunWithResult` | 기본 스크립트의 판단 결과에서 주문 의도를 만든다. 기존 매수·매도 스크립트가 조작하는 `HasPosition`은 실거래의 보유 증거로 사용하지 않는다. 실거래 평가에는 조회한 보유·매도 가능 수량과 확인된 체결을 공급한다. |
| `StrategyEvolutionRuntime` → `PaperTradingService` | 활성 전략의 신호 평가를 별도로 재사용한다. 페이퍼 진입·청산과 실주문 실행을 각각 기록하며, 실거래 평가의 보유 수량은 실계좌 상태에서 받는다. |
| `IStockOrderService` → `StockOrderService` | 현재 COM 리소스의 `CSPAT00600` 신규 주문을 사용한다. 응답의 주문번호와 상태를 주문 원장에 기록한다. 지원되는 정정·취소는 원주문번호와 미체결 수량을 확인한 사용자 동작에 연결한다. |
| `AccountService`의 SC0~SC4 구독 | 종목·계좌·주문번호·체결 식별자·수량·가격을 담은 주문 이벤트를 게시한다. 주문 원장과 Summary가 같은 이벤트를 소비한다. |
| Summary | 기존 `CSPAQ12300` 잔고 및 `FOCCQ33600` 기간 수익률 갱신 흐름을 사용한다. 개별 주문의 체결 여부는 주문 원장에 표시한다. |

LS증권 문서에서 SC0은 주문 접수, SC1은 체결, SC2는 정정, SC3은 취소, SC4는 거부로 분류된다. 주문 대사에는 `CSPAQ13700` 또는 `t0425`를 후보로 두고, 사용 중인 Xing COM 환경에서 조회 범위와 응답 필드를 확인한 뒤 하나를 선택한다. REST 예제의 주문 TR 번호와 필드를 COM 구현에 그대로 적용하지 않는다. ## 3. 주문 처리와 복구

1. 전략 실행 결과에서 계좌, 전략 ID·버전, 종목, 판단 시각, 매수·매도 방향, 기준가와 신호 수량을 담은 주문 의도를 생성한다. 시뮬레이션·페이퍼 신호에는 별도 출처를 부여하고, 계좌·종목마다 한 실주문 실행 경로만 활성화한다.
2. 주문 실행 서비스에서 최신 호가와 거래 가능 상태, 계좌 일치, 보유·매도 가능 수량, 미체결을 반영한 예수금, 주당·종목당·일일 한도를 확인한다. 지정가는 호가 단위에 맞추고 주문 직전에 동일 조건을 다시 검사한다. 비밀번호는 세션 메모리에서만 사용하며 원장·로그·설정 파일에는 기록하지 않는다.
3. 주문 의도 ID에 고유 제약을 둔 SQLite 원장을 추가한다. 주문을 보내기 전에 의도와 요청 수량·가격을 저장하고 계좌·종목별로 직렬 처리한다. 같은 신호의 재처리와 미체결 중 반대 신호는 중복 주문 대신 사유를 기록한다. 주문 서비스를 UI 이벤트에서 직접 호출하지 않는다.
4. 주문번호를 받은 상태는 **접수**로 표시한다. SC1의 개별 체결은 계좌·거래일·주문번호·체결 식별자로 중복 제거한 뒤 누적 수량과 평균 체결가에 반영한다. SC 이벤트가 주문 응답보다 먼저 오면 보관했다가 주문번호가 확인된 뒤 연결한다. 증권사가 확정한 보유분과 기존 사용자 보유분은 출처를 구분해 표시한다.
5. 주문 응답 시간 초과나 연결 끊김으로 제출 여부가 불명확하면 **확인 필요**로 남긴다. 동일 의도를 자동 재전송하지 않고 증권사의 주문·체결·미체결 내역과 대사한다. 재연결 시 미확정 주문과 실제 보유를 복구한 뒤에만 실주문을 다시 활성화할 수 있다.
6. 화면에 **실주문 중지**를 제공한다. 중지하면 신규 주문을 차단하고 이미 접수된 미체결 주문은 목록에 남긴다. 취소 요청은 별도의 사용자 동작으로 처리하고, 증권사의 취소 확인이 도착할 때까지 상태를 유지한다.

## 4. 구현 순서와 검증 기준

| 단계 | 구현 및 완료 기준 |
| --- | --- |
| 1. 주문 원장과 계좌 이벤트 | 가짜 주문 서비스로 접수, 부분 체결, 전량 체결, 거부, 취소를 재생한다. 중복·역순 이벤트와 외부 주문을 주입해 상태가 뒤로 돌아가거나 포지션이 중복 반영되지 않는지 확인한다. |
| 2. 전략 연결과 주문 한도 | 기본 전략·활성 전략에서 동일 계좌·종목의 반복 신호가 단일 주문 의도로 처리되는지 확인한다. 한도 초과, 부족한 잔고, 오래된 호가, 세션 전환, 정지 상태에서 신규 요청이 발생하지 않는지 검증한다. |
| 3. 대사와 운영 화면 | 응답 누락 직후 재시작하거나 부분 체결 중 연결을 끊어도 증권사 조회 결과로 복구하고 재주문하지 않아야 한다. 주문 화면·차트·Summary가 같은 계좌의 확인된 이벤트만 표시하는지 확인한다. |
| 4. Xing 모의 환경 | 실제 COM 요청·응답과 SC 이벤트를 주문번호로 대조한다. 주문 접수, 체결, 미체결 취소와 Summary 갱신까지 재현하고 실계좌 연결 여부를 화면에 표시한다. |
| 5. 실계좌 제한 검증 | 별도로 승인한 계좌·종목·수량·가격 한도 안에서 지정가 주문을 사용한다. 증권사 화면과 앱의 주문번호·체결수량·평균 체결가를 대조하고 주문 중지와 복구 동작을 확인한 뒤 배포 범위를 확대한다. |
